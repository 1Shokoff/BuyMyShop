# BuyMyShop

Страница оплаты для внешнего магазина: покупатель приходит по кнопке «Купить»
со стороннего сайта, читает инструкцию, вводит 15-значный номер, выбирает
платёжный агрегатор и оплачивает. После подтверждения оплаты номер уходит
в Telegram-бот продавца, а покупатель видит результат на странице заказа.

## Как устроен поток

```
Внешний магазин ──► GET /                     страница товара: инструкция, поле, выбор агрегатора
                      │
                      ▼ POST /buy             создаётся заказ + попытка оплаты, 303 на форму агрегатора
                      │
        ┌─────────────┴──────────────┐
        ▼                            ▼
  POST /webhooks/{провайдер}    GET /return/{payment_id}
  подпись → сверка по API       сверка статуса по API, затем 303 на страницу заказа
        │
        ▼
  заказ → paid (ровно один раз) ──► строка в outbox ──► фоновый воркер ──► Telegram
```

### Главный принцип

**Статус оплаты никогда не берётся из редиректа возврата.** Возврат покупателя —
это его браузер, параметры в адресной строке подделываются руками. Заказ
переводится в `paid` только после:

1. проверки IP отправителя (там, где агрегатор публикует свои диапазоны);
2. проверки подписи уведомления — либо, если агрегатор не подписывает
   уведомления (ЮKassa), контрольного запроса статуса по его API;
3. проверки, что событие ещё не обработано (журнал `webhook_events`);
4. сверки суммы платежа с суммой заказа.

Переход в `paid` делается одним `UPDATE ... WHERE status <> 'paid'`, поэтому
повторная доставка вебхука не задваивает уведомление в Telegram.

## Стек

Python 3.12 · FastAPI · SQLAlchemy 2 (async, psycopg 3) · PostgreSQL 16 ·
Alembic · Jinja2 · Docker Compose · Caddy (TLS Let's Encrypt автоматически).

## Структура

```
app/
  config.py            настройки из окружения
  models.py            orders, payments, webhook_events, outbox_messages
  security.py          CSRF-токены, лимит частоты запросов
  payments/            по одному модулю на агрегатор + общий контракт в base.py
  routes/              public (оплата и статус), webhooks, admin, dummy
  services/            orders (жизненный цикл), telegram (outbox), content (тексты)
  templates/, static/
content/               тексты инструкции и правовых документов (правятся без пересборки)
migrations/            Alembic
tests/                 подписи провайдеров, валидация, уведомления, CSRF и лимиты
```

## Запуск локально

```bash
cp .env.example .env          # заполнить SECRET_KEY, POSTGRES_PASSWORD, SITE_DOMAIN
docker compose up -d --build
```

Приложение само применяет миграции при старте (`docker/entrypoint.sh`).

Чтобы проверить весь сценарий без реальных денег, включите встроенную заглушку:

```
DUMMY_ENABLED=true
```

Появится способ оплаты «Тестовая оплата», который отправляет подписанное
уведомление на собственный `/webhooks/dummy` — то есть проходит ровно тот путь,
по которому пойдут боевые агрегаторы. **В проде должно быть `false`.**

## Развёртывание на сервере

1. Направьте A-запись домена (и `www`, если нужен) на IP сервера.
2. Установите Docker и Docker Compose, склонируйте репозиторий.
3. Заполните `.env`: `SITE_DOMAIN`, `PUBLIC_BASE_URL` (тот же домен, `https://`),
   `ACME_EMAIL`, `SECRET_KEY` (`openssl rand -hex 32`), `POSTGRES_PASSWORD`,
   параметры товара, ключи агрегаторов, токен Telegram.
4. `docker compose up -d --build`. Caddy сам получит сертификат Let's Encrypt.
5. В кабинете каждого агрегатора укажите адрес уведомлений
   `https://<домен>/webhooks/<провайдер>` и адреса возврата
   `https://<домен>/return/{payment_id}` — их подставляет само приложение.

Порт Postgres наружу не публикуется: база доступна только внутри compose-сети.

### Резервные копии

Тома `pgdata`, `caddy_data` переживают пересоздание контейнеров. Отдельный cron
для `pg_dump` пока не настроен — это следующий шаг после запуска.

## Подключение агрегаторов

Каждый провайдер включается своим флагом и работает независимо от остальных.
Список включённых пишется в лог при старте.

| Провайдер | Флаг | Что заполнить |
|---|---|---|
| Robokassa | `ROBOKASSA_ENABLED` | `MERCHANT_LOGIN`, `PASSWORD1`, `PASSWORD2`, `HASH_ALGORITHM` |
| ЮKassa | `YOOKASSA_ENABLED` | `SHOP_ID`, `SECRET_KEY` |
| Lava | `LAVA_ENABLED` | `API_KEY`, `WEBHOOK_SECRET`, `OFFER_ID` |
| Enot.io | `ENOT_ENABLED` | `SHOP_ID`, `SECRET_KEY`, `ADDITIONAL_KEY` |

### Что обязательно сверить перед боем

Документация ЮKassa, Lava и Enot была недоступна из среды, где писался код
(закрыта сетевой политикой), поэтому часть деталей взята из общих сведений об
этих API. Места, требующие сверки, помечены в коде комментарием `СВЕРИТЬ`:

* **ЮKassa** — список IP-диапазонов уведомлений (`DEFAULT_WEBHOOK_NETWORKS`
  в `app/payments/yookassa.py`). Если диапазоны изменились, уведомления будут
  отклоняться с 403; в журнале `webhook_events` это видно сразу.
* **Robokassa** — расшифровка кодов `OpState` (`OPSTATE_SUCCESS`/`OPSTATE_FAILED`).
  Формулы подписей сверены и покрыты тестами.
* **Lava** — URL создания счёта, имена полей, заголовок и формула подписи вебхука.
* **Enot.io** — URL создания счёта, имя заголовка подписи, правило канонизации
  тела перед HMAC.

Формулы подписей вынесены в отдельные функции и покрыты тестами, поэтому правка —
одно место в одном файле. Lava и Enot по умолчанию выключены.

### Про статус самозанятого

Robokassa и ЮKassa работают с плательщиками НПД и формируют чеки сами
(у Robokassa это «Робочеки СМЗ» с привязкой к «Мой налог»). Поэтому
`YOOKASSA_SEND_RECEIPT` по умолчанию `false`, а в запрос Robokassa параметр
`Receipt` не передаётся — иначе фискализация задвоилась бы. Если конкретный
кабинет требует передавать состав чека, включите флаг и заполните
`YOOKASSA_VAT_CODE`; для чека агрегатору нужен контакт покупателя, то есть
`COLLECT_EMAIL=true` и, скорее всего, `REQUIRE_EMAIL=true`.

## Telegram

1. Создайте бота у `@BotFather`, получите токен → `TELEGRAM_BOT_TOKEN`.
2. Узнайте `chat_id` (напишите боту и откройте
   `https://api.telegram.org/bot<токен>/getUpdates`) → `TELEGRAM_CHAT_ID`.

Уведомления не отправляются напрямую из обработчика вебхука: они кладутся
в таблицу `outbox_messages` в одной транзакции с переводом заказа в `paid`.
Фоновый воркер доставляет их с повторами и экспоненциальной задержкой
(до `TELEGRAM_MAX_ATTEMPTS` попыток). Если Telegram лежал — сообщение уйдёт
позже, а не потеряется.

## Админка

`/admin`, вход по HTTP Basic (`ADMIN_USERNAME` / `ADMIN_PASSWORD`).
Список заказов с фильтром по статусу и поиском, карточка заказа с историей
платежей и уведомлений, кнопка повторной отправки в Telegram.
Пустой `ADMIN_PASSWORD` полностью выключает раздел (отдаёт 404).

## Правовые документы

`/offer`, `/privacy`, `/refund`, `/contacts` рендерятся из `content/legal/*.md`.
Тексты — **черновики с пометками «ЗАПОЛНИТЕ»**: их нужно вычитать и заполнить
до подачи заявки агрегаторам, иначе модерация не пропустит сайт.

## Настройка поля с ID клиента

Поле описывается настройками, а не кодом:

```
CUSTOMER_FIELD_LABEL=ID клиента
CUSTOMER_FIELD_HINT=15 цифр, без пробелов и дефисов
CUSTOMER_FIELD_PATTERN=^\d{15}$
CUSTOMER_FIELD_ERROR=Введите ровно 15 цифр.
REQUIRE_REF_CONFIRMATION=true
```

Перед проверкой из введённого значения убираются пробелы, дефисы и подчёркивания,
поэтому вставка «123 456 789 012 345» из буфера работает.

Исправить ID после оплаты нельзя, поэтому форма защищена от опечатки с двух сторон:
под полем показывается введённое значение, разбитое по три цифры, со счётчиком
длины, а отправка требует галочки «я проверил ID». Галочка проверяется на сервере,
а не только атрибутом `required`; отключается через `REQUIRE_REF_CONFIRMATION=false`.

  валюту и выбора на форме.
